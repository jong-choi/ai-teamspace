# 01. 측정 1: 고치기 전 상태

아무것도 고치지 않은 상태로 26개 케이스를 한 번 돌린 결과다. 이후 회차는 모두 이 결과와 비교한다.

- 실행 횟수는 1회다. 한두 건 차이는 우연일 수 있으므로, 이후 회차에서는 원본에서 원인이 확인된 변화만 개선으로 적는다.
- [시험 실행](00-shakedown.md)과 달리 승인 대기로 끝난 실행도 대화가 원본에 남는다. 그래서 쓰기 실패의 원인을 모두 확인할 수 있었다.
- 판정 기준은 [README](README.md#판정-기준)에 있다.

## 도구 호출 정확도

실패와 반복의 원인을 원본에서 확인한 순서대로 적는다.

### 1. 오류 문구가 원인을 알려 주지 않는다

스키마에 안 맞는 호출 41건이 전부 같은 문구로 거부됐다. 어느 인자가 왜 틀렸는지가 없다.

- 모델이 받은 문구는 `Received tool input did not match expected schema` 한 줄과 서버 내부 호출 스택이다. 스택은 수십 줄이고 서버 파일 경로가 들어 있다.
- 모델이 틀린 인자를 짚지 못하고 값을 이것저것 바꿔 본다. `members-admins`에서는 빈 `search`가 원인인데 `role` 값만 9번 바꿨다.
- `ticket-create-with-due`에서는 마감 시각 형식이 원인인데 우선순위를 대문자로 바꿨다.
- 오류를 받은 뒤 도구 설명을 찾으려고 `grep`을 부른다. `grep` 36회가 모두 이 흐름이다. 에이전트의 가상 파일 시스템은 비어 있어서 항상 결과가 없다.

### 2. 선택 인자를 빈 값으로 채운다

값이 없는 선택 인자를 생략하지 않고 빈 문자열이나 `null`로 보낸다. 최소 길이나 형식 제약에 걸려 거부된다.

- `calendar_meetings_list`에 `category`, `projectId`, `roomId`, `search`를 모두 빈 문자열로 보냈다. 회의 목록을 부른 케이스 5개 모두에서 나왔다.
- `organization_members_list`의 `search`, `chat_messages_list`의 `before`도 같다.

### 3. 없는 값을 지어낸다

허용 값 목록이 스키마에 있는데도 다른 값을 보낸다.

| 도구                          | 인자           | 보낸 값                       | 허용 값                           |
| ----------------------------- | -------------- | ----------------------------- | --------------------------------- |
| `knowledge_search`            | `mode`         | `default`, `simple`, `search` | `hybrid`, `semantic`, `keyword`   |
| `knowledge_search`            | `limit`        | 100                           | 1~20                              |
| `calendar_meeting_create`     | `category`     | `Meeting`, `meeting`          | `team`, `sprint`, `1on1` 등       |
| `calendar_meeting_create`     | `locationType` | `meetingRoom`, `text`         | `online`, `meeting_room`, `other` |
| `calendar_meeting_reschedule` | `scope`        | `instance`                    | `single`, `series`, `future`      |
| `organization_members_list`   | `role`         | `ADMIN`, `OWNER`, `ALL`       | `owner`, `admin`, `member`        |

1번 때문에 틀린 값을 고칠 단서가 없어서 같은 값을 다시 보낸다.

### 4. 참석자 필터 때문에 자기가 주최한 회의를 못 찾는다

모델은 회의를 찾을 때 `attendeeUserId`에 사용자 본인 ID를 넣는다. 이 필터는 참석자로 초대된 회의만 돌려주고, 주최만 한 회의는 뺀다. 인자 설명이 없어서 모델은 이 차이를 알 수 없다.

- `meeting-cancel`: 사용자가 주최한 1:1 회의가 결과에 없어서 끝내 못 찾았다.
- `meeting-reschedule`: 같은 이유로 못 찾다가 지식 그래프 검색으로 우회해서 찾았다.
- `meetings-list-week`: 통과했지만 11건 중 6건이 빠졌다.

### 5. 승인을 받고 나서야 인자 오류가 드러난다

쓰기 도구는 실행 전에 사용자 승인을 받는다. 인자 검증은 승인 뒤에 일어난다. 그래서 사용자는 실패할 호출을 승인하게 되고, 모델이 고쳐 보낼 때마다 다시 승인을 요청받는다. 쓰기 실패 7건 중 4건이 승인 요청 3번에서 멈췄다.

### 6. 수정 도구가 없는 인자를 조용히 버린다

`wiki-body-edit-unsupported`에서 모델은 `wiki_document_update`에 본문 인자를 넣었다. 이 도구는 본문을 받지 않는다. 스키마가 모르는 인자를 막지 않아서, 승인됐다면 본문은 그대로인데 성공으로 끝났을 것이다. 도구 설명에는 본문을 못 바꾼다는 말이 없다.

### 7. 날짜 형식이 도구마다 다르다

티켓 마감 시각은 `Z`로 끝나는 UTC만 받는다. 캘린더 도구는 `+09:00` 같은 오프셋을 받고, 시스템 컨텍스트도 오프셋 형식으로 현재 시각을 알려 준다. 모델은 티켓에도 오프셋 형식을 보냈다가 거부됐다.

### 8. 필요한 정보를 주는 도구를 못 고른다

- `project-progress`: 진행 중 티켓 수는 `projects_list` 결과에 있다. 도구 설명에 그 말이 없어서 지식 그래프 검색으로 갔다.
- `meeting-create-in-room`: 회의실 ID를 얻을 도구가 없다. 위키와 지식 그래프를 7번 검색하고도 찾지 못했다. 회의실 ID는 그 회의실을 쓰는 다른 회의의 조회 결과에만 있다.
- `ticket-create-with-due`: 컬럼 ID를 티켓 ID 자리에 넣어 티켓 조회를 불렀다.
- `members-admins`: 역할 필터를 쓰지 못하고 전체 멤버의 첫 10명만 조회했다.

## 도구 오류 메시지

자연스럽게 난 오류 46건을 종류별로 봤다.

| 종류               | 건수 | 모델이 받은 문구                   | 다음 호출에서 고쳤는가                        |
| ------------------ | ---- | ---------------------------------- | --------------------------------------------- |
| 스키마 검증 거부   | 41   | 원인 없는 한 줄과 호출 스택        | 대부분 못 고침. 같은 도구를 여러 번 다시 부름 |
| 없는 도구 호출     | 3    | 쓸 수 있는 도구 이름 목록          | 바로 고침                                     |
| 잘못된 메시지 커서 | 1    | `유효하지 않은 메시지 커서입니다.` | 바로 고침. 무엇을 넣어야 하는지는 없음        |
| 티켓 없음          | 1    | `티켓을 찾을 수 없습니다.`         | 바로 고침                                     |

서버가 만든 오류 문구는 짧고 원인이 분명해서 모델이 바로 고쳤다. 문제는 스키마 검증 거부 문구 하나다. 이 문구는 서버가 아니라 에이전트 쪽 도구 실행 계층에서 만들어진다.

틀린 답 2건:

- `wiki-find-and-read`: 문서에 없는 금요일 오전 배포 시간을 만들어 냈다.
- `members-admins`: 멤버 12명 중 10명만 조회하고 관리자가 2명이라고 단정했다. 실제로는 관리자가 1명 더 있다.

지식 그래프를 쓴 3건:

- 그래프가 돌려준 관계는 방향까지 맞게 옮긴다. `knowledge-relations`는 관계 2개, `knowledge-refund-settlement`는 관계 3개를 맞게 옮겼다.
- 그 위에 그래프에 없는 관계를 같은 표에 섞어 적는다. `knowledge-refund-settlement`는 표 8줄 중 5줄이 지어낸 관계 이름이다. 사용자는 어느 줄이 그래프에서 온 것인지 구분할 수 없다.
- 문서 본문에서 온 내용(환불 규칙, 장애 대응 순서)은 세 건 모두 문서와 일치한다.

그 밖에:

- `meetings-list-week`는 도구 결과를 그대로 옮겼지만, 필터 때문에 일부만 온 결과를 전체인 것처럼 답했다.
- `chat-messages-read`, `knowledge-incident-response`는 원문에 없는 표현과 예시를 조금 덧붙였다.
- 시각은 UTC와 KST가 섞여 나온다. `ticket-read-by-title`은 KST로 맞게 바꿨고, `projects-list`는 UTC 그대로 적었다.

## 트레이싱

- 26개 케이스의 실행 43개가 모두 Langfuse 트레이스와 연결됐다. 회차 이름으로 걸러 볼 수 있다.
- 모델 호출, 도구 실행, 승인 단계가 관측으로 남고, 도구 입력의 조직 ID는 가려진다.
- 스키마 검증에서 거부된 호출은 도구 관측으로 남지 않는다. `members-admins`의 멤버 조회는 10번 중 성공한 1번만 도구 관측이다. 거부된 호출은 도구 실행 단계의 출력 글자에만 있고 수준도 오류로 표시되지 않아서, Langfuse에서 오류만 걸러 볼 수 없다.
- 거부 문구 안에는 조직 ID와 서버 파일 경로가 가려지지 않은 채 들어 있다.
- 충실도와 응답 품질 판정은 Langfuse 점수로 올리지 않았다. 이 문서에만 있다.

## 측정 중 발견한 운영 문제

첫 시도에서 평가용 큐 Redis가 메모리 한도 256MB에 걸려 실행이 멈췄다. 에이전트 실행의 재생용 스트림이 기본 보존 시간 동안 쌓인 것이 원인이다. 평가 스크립트는 회차마다 Redis를 비우고 보존 시간을 10분으로 줄여서 돌린다. 실행이 많은 운영 환경에서도 같은 일이 생길 수 있다.
