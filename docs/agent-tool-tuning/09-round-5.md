# 09. 5차 개선과 측정

[07 문서](07-round-4.md)에 남긴 문제를 고치고 1회 측정했다. 비교 대상은 4차 개선본(07 문서, 1회)이다.

## 고친 것

| 문제 (07 문서)                    | 수정                                                                                                   |
| --------------------------------- | ------------------------------------------------------------------------------------------------------ |
| 그래프 관계를 틀리게 옮김         | `knowledge_search`가 문서의 관계 전부가 아니라 양 끝 개념 이름에 검색어 낱말이 든 관계만 돌려준다      |
|                                   | 도구 설명에 "relations에 없는 관계는 관계로 적지 않습니다"를 넣었다                                    |
| 결과에 영향 없는 조회를 끼워 넣음 | 티켓을 제목으로 찾는 `project_tickets_list` 도구를 추가했다                                            |
| `wiki_search`에 없는 인자를 넣음  | `wiki_search`가 `limit`을 받는다. 설명에 "검색 방식은 고를 수 없습니다"를 넣었다                       |
| 답에 내부 ID를 적음               | 시스템 프롬프트의 문장을 바꿨다. "ID는 도구 호출에 쓰는 값이니 사용자가 묻지 않으면 답에 쓰지 마세요." |

승인 전 인자 검증은 에이전트의 승인 구조를 바꿔야 해서 넣지 않았다.

도구 문구 크기:

| ------------------ | ------ | ------ |

## 한계

- 실행 횟수는 1회(26건)다. 비교 대상도 1회다.
- 같은 코드의 하네스 통과가 2건 흔들린다(04 문서). 1회끼리의 작은 차이는 근거로 쓰지 않는다.
- 판정 점수 182개가 모두 붙었다. 도구 결과가 잘린 건은 없다.

## 지식 그래프

`knowledge_search`가 돌려준 관계 수:

| 케이스                      | 4차 (관계 수) | 5차 (관계 수) |
| --------------------------- | ------------- | ------------- |
| knowledge-refund-settlement | 83            | 7             |
| knowledge-relations         | 78            | 10            |
| knowledge-incident-response | 42            | 14            |

판정 점수와 원본 대조:

| 케이스                      | 4차 | 5차  | 원본 대조                                                                                                                                                               |
| --------------------------- | --- | ---- | ----------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| knowledge-refund-settlement | 0.5 | 1.0  | 답에 적은 관계 4개가 모두 그래프에 있다. 4차는 관계 표 9줄 중 그래프에 있는 것이 3종류였다                                                                              |
| knowledge-relations         | 0.5 | 0.33 | 판정이 지나치다. 답의 관계 2개(`Go/No-Go 회의 → 앱`, `출시 여부 → Go/No-Go 회의`)는 그래프와 같다. 표가 회의 기준으로 연결 대상을 적은 것을 방향이 뒤집힌 것으로 읽었다 |
| knowledge-incident-response | 0.5 | 0.5  | 판정이 지나치다. 절차를 묻는 요청이라 관계를 적지 않은 것을 감점했다                                                                                                    |

- 원본과 대조하면 그래프에 없는 관계를 덧붙인 답은 4차 1건에서 5차 0건이다. 방향을 틀린 답도 0건이다.
- `knowledge-relations`의 답은 회의 레코드(`릴리스 Go/No-Go`)를 연결 대상 표에 함께 적었다. "회의(레코드)"라고 구분해 적었다.
- 환불·정산 질문은 도구를 5번 불렀다(위키 검색 2번, 지식 검색, 문서 조회, 주변 관계 조회). 4차에는 지식 검색 1번이었다. 2·3차에도 3~6번이어서 관계를 줄인 탓이라고 말할 수는 없다.
- 판정 점수 평균은 0.61에 머문다. 세 건 중 두 건이 판정 문제다. 이 점수는 판정 프롬프트를 고치기 전에는 더 오르기 어렵다.

## 도구 결과 충실도

26건 중 1 미만은 3건이다.

| 케이스                     | 점수 | 판정 근거                               | 원본 대조                                                                                         |
| -------------------------- | ---- | --------------------------------------- | ------------------------------------------------------------------------------------------------- |
| wiki-find-and-read         | 0.5  | 평일을 월~목으로 좁혀 적었다            | 맞는 지적. 위키는 "평일 오전 11시~오후 4시, 금요일 오후 제외"인데 답은 "평일(월~목)"이라고 적었다 |
| ticket-create-with-due     | 0.5  | 프로젝트를 '한라봉 스튜디오'라고 적었다 | 맞는 지적. 한라봉 스튜디오는 조직 이름이고 프로젝트는 '귤밭 앱 리뉴얼'이다                        |
| wiki-body-edit-unsupported | 0    | 수정 기능이 없다는 말의 근거가 없다     | 판정 오류                                                                                         |

판정 모델이 놓친 것이 1건 있다. `project-columns-from-screen`도 프로젝트를 '한라봉 스튜디오'라고 적었는데 충실도 1.0을 받았다.

- 실제 문제는 3건(26건 중 12%)이다. 4차는 2건(8%)이었다.
- 프로젝트 이름 오류는 컬럼 목록과 티켓 생성 결과에 프로젝트 이름이 없어서 생긴다. 모델이 맥락 블록의 조직 이름을 프로젝트 이름으로 적는다. 2차에도 1건 있었다. 이번 회차의 변경이 원인이라는 근거는 없다.
- `wiki-find-and-read`는 요청 달성과 시각 정확성에서도 0점을 받았다. 같은 문장 하나 때문이다. 이 케이스는 2차에 2건, 3차에 0건, 4차에 0건, 5차에 1건으로 실행마다 오락가락한다.

## 도구 호출 정확도

도구 호출 45회 중 오류 0회다.

| 수정                        | 실행 기록                                                                                           |
| --------------------------- | --------------------------------------------------------------------------------------------------- |
| `wiki_search`의 `limit`     | `limit`을 넣은 호출 4회가 모두 성공했다. 3차까지는 이 인자로 거부됐다                               |
| `project_tickets_list` 추가 | 0회 호출. 티켓을 제목으로 찾는 3건 모두 지난 회차처럼 `knowledge_search`(키워드)로 티켓 ID를 얻었다 |

- 티켓 목록 도구를 추가했지만 모델은 쓰지 않았다. 티켓을 찾는 경로는 그대로다.
- 그 경로의 호출 수는 줄었다. `ticket-priority-update`는 4차에 지식 검색을 세 번 했고 5차에는 한 번 했다. 1회끼리의 비교라 새 도구나 설명 때문이라고 말할 수 없다.
- 판정 모델의 감점 1건(`ticket-move-to-review` 0.5)은 맞는 지적이다. 티켓을 옮기기 전에 상세를 한 번 조회했다. 결과는 맞다.

## 응답 품질

26건 모두 1.0이다.

답에 내부 ID가 나온 것은 `meeting-create` 1건이다. 회의를 만든 뒤 회의 ID를 적고 "이 ID로 상세를 확인할 수 있다"고 안내했다. 4차에 ID를 적은 두 케이스(`project-columns-from-screen`, `knowledge-incident-response`)는 이번에 ID가 없다. 한 케이스에서 사라지고 다른 케이스에서 나온 것이어서, 프롬프트 문장을 바꾼 효과라고 말할 수 없다.

## 트레이싱

- 26건 모두 채점용 관측이 올라갔고 판정 점수가 빠짐없이 붙었다.
- 판정이 틀리거나 지나친 것은 3건이다(지식 그래프 2건, 충실도 1건). 판정이 놓친 것이 1건이다.

## 남은 문제

- 컬럼 목록과 티켓 쓰기 결과에 프로젝트 이름이 없어 모델이 조직 이름을 프로젝트 이름으로 적는다(26건 중 2건).
- 위키의 배포 시간대를 답할 때 요일 범위를 문서와 다르게 적는 일이 실행마다 오락가락한다.
- `project_tickets_list`가 쓰이지 않는다. 티켓은 여전히 지식 검색을 거쳐 찾는다.
- 회의를 만든 뒤 회의 ID를 답에 적는 일이 남아 있다(26건 중 1건).
- 승인 전 인자 검증이 없다.
- 판정 모델이 지식 그래프 충실도를 요청과 무관하게 감점한다.
