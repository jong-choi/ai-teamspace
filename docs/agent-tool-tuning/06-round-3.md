# 06. 3차 개선과 측정

[05 문서](05-round-2.md)에서 고른 충실도와 응답 품질 문제를 고치고 2회 측정했다. 비교 대상은 2차 개선본(05 문서, 2회)이다.

## 고친 것

| 문제 (05 문서)                        | 수정                                                                                                          |
| ------------------------------------- | ------------------------------------------------------------------------------------------------------------- |
| 답에 요일을 틀리게 적음               | 도구 결과의 UTC 시각을 사용자 시간대의 시각과 요일로 바꿔 모델에게 준다                                       |
| 채팅 메시지 결과에 발신자 이름이 없음 | `chat_messages_list` 결과에 참여자의 ID와 이름을 넣는다                                                       |
| 확인하지 않은 일을 단정, 내부 ID 노출 | 시스템 프롬프트에 한 문장 추가: "답에는 도구 결과로 확인한 사실만 쓰고, 사용자가 묻지 않은 ID는 쓰지 마세요." |

도구 결과의 시각은 이렇게 바뀐다.

```text
"startAt":"2026-10-21T05:00:00.000Z"
"startAt":"2026-10-21T14:00:00+09:00 (Wednesday)"
```

05 문서에서 3차 대상으로 적은 것 중 기본 파일 도구(`ls`, `grep`) 호출과 `wiki_search`에 없는 인자를 넣는 것은 고치지 않았다.

## 한계

- 실행 횟수는 2회(52건)다. 비교 대상도 2회다.
- 같은 코드의 하네스 통과가 2건 흔들린다(04 문서). 그보다 작은 차이는 근거로 쓰지 않는다.
- 판정 점수 364개 중 1개가 붙지 않았다(`knowledge-refund-settlement` 2회차의 충실도).
- 도구 결과가 잘린 건은 없다.

- 프롬프트 한 문장은 문서 내용을 부풀리는 것을 막았지만 알림 문장은 막지 못했다. 회의 쓰기 10건 중 5건에 알림 문장이 그대로 있다.

## 시각 정확성

거짓은 52건 중 1건이다. `meeting-reschedule` 2회차가 원래 일정을 "오전 2시"로 적었다.

날짜에 요일을 붙여 적은 실행:

| 회차              | 요일을 적은 실행 | 틀린 실행 |
| ----------------- | ---------------- | --------- |
| 1차 개선본 (26건) | 3건              | 2건       |
| 2차 개선본 (52건) | 3건              | 1건       |
| 3차 개선본 (52건) | 6건              | 0건       |

3차에서 요일을 적은 것은 회의실 회의 생성 2건, 일정 변경 1건, 참석 응답 1건, 이번 주 회의 목록 2건이다. 모두 도구 결과의 요일과 같다.

새로 드러난 문제가 하나 있다. 승인을 거친 쓰기 도구의 결과는 시각이 UTC로 나온다.

```text
"startAt":"2026-10-16T06:00:00+00:00 (Friday)"
```

승인 뒤 실행을 이어 갈 때는 클라이언트가 시간대를 다시 보내지 않아 UTC로 처리된다. 시각이 든 도구 결과 78개 중 22개가 이렇게 나왔다. 조회 결과는 한국 시각으로, 쓰기 결과는 UTC로 나와 한 대화 안에서 시간대가 섞인다. `meeting-reschedule` 2회차의 "오전 2시"가 이 섞임에서 나왔는지는 확인하지 못했다.

## 도구 호출 정확도

오류 3회는 모두 2회차에서 나왔다.

| 케이스                      | 호출                             | 오류 메시지                                              | 다음 호출                               |
| --------------------------- | -------------------------------- | -------------------------------------------------------- | --------------------------------------- |
| knowledge-relations         | `knowledge_search`에 `limit: 50` | `limit: 허용 값은 1~20 정수입니다.`                      | 다른 도구로 넘어갔다가 20으로 다시 부름 |
| knowledge-incident-response | `wiki_search`에 `limit`          | `limit: 이 도구에 없는 인자입니다.`                      | 인자를 빼고 성공                        |
| wiki-create                 | `wiki_search`에 빈 검색어        | `q: 허용 값은 200자 이하의 비어 있지 않은 문자열입니다.` | 검색을 그만두고 문서 생성               |

필요 없는 호출 6회:

| 케이스                             | 호출                   |
| ---------------------------------- | ---------------------- |
| wiki-body-edit-unsupported (2회차) | `glob`, `grep`, `ls`   |
| wiki-body-edit-unsupported (1회차) | `grep`                 |
| knowledge-relations (1회차)        | `grep`                 |
| knowledge-relations (2회차)        | 회의 조회 등 중복 조회 |

- 기본 파일 도구 호출이 5회다. 2차는 2회였다. 본문 수정 도구나 문서 ID를 파일 시스템에서 찾으려 한다.
- `knowledge-relations`는 두 실행 모두 검색을 6~7번 했다. 2차는 1번이었다. 요청에 맞는 결과를 첫 검색에서 얻고도 계속 찾았다.
- 빈 선택 인자, 회의 분류 값, 회의실 지정, 참석자 필터 문제는 3차에서도 0건이다.

판정 모델의 도구 선택 감점 10건 중 2건(`wiki-rename`의 문서 조회, `ticket-read-by-title`의 맥락 조회)은 결과에 영향이 없는 조회 1번이다.

## 트레이싱

- 52건 모두 채점용 관측이 올라갔다. 판정 점수 1개가 붙지 않았다.
- 판정 모델은 모델이 본 도구 결과(시각이 바뀐 뒤)를 그대로 본다.
- 판정 오류는 2차와 같은 종류다. 도구 없이 답하는 케이스의 충실도 0점, 도구 설명에 있는 사실을 근거 없다고 보는 것. 52건 중 4건이다.

## 다음 수정

4차 개선에서 다룬다.

- 승인 뒤 쓰기 도구 결과의 시각이 UTC로 나오는 것.
- 쓰기 요청 뒤 알림 전송을 단정하는 것.
- 기본 파일 도구(`ls`, `grep`, `glob`)를 부르는 것.

남는 문제:

- 그래프 관계 표에 다른 도구에서 얻은 사실을 섞는 것.
- 회의 생성 뒤 회의 ID를 답에 적는 것.
- `wiki_search`에 없는 인자를 넣는 것.
- 승인 전 인자 검증.
